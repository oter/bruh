# bruh v0.1 implementation plans (index)

**Spec:** [../../spec.md](../../spec.md) version 0.4, approved 2026-09-30.

Version 0.1 contains all parts of the specification (owner decision 2026-09-30). The work is split into six plans because the specification covers six subsystems. Each plan produces software that works and is tested on its own. The plans run in this order, because later plans depend on the probe results and the interfaces of earlier plans.

| # | Plan | Delivers | Depends on |
|---|---|---|---|
| 1 | [Foundation and probes](2026-09-30-plan-1-foundation.md) | Repository skeleton, license, CI, the probe results for every "Verify" item that later plans depend on, and the bruh MCP server with all its tools | none |
| 2 | [Hooks, status line tap, and init skill](2026-09-30-plan-2-hooks-init.md) | `statusline-tap.sh`, `handoff-nudge.sh`, `handoff-inject.sh`, `lease-guard.sh`, `hooks.json`, `/bruh:init` (interactive and non-interactive) | 1 |
| 3 | [Roles and the ledger](2026-09-30-plan-3-roles-ledger.md) | `agents/bigm.md`, `agents/clanker.md`, `agents/clerk.md`, the launch procedure, `defaults/priorities.md`, `defaults/house-rules.md`, the ledger template | 1, 2 |
| 4 | [The `deliver` workflow](2026-09-30-plan-4-deliver.md) | `workflows/deliver.js` with the question path of spec 6.2 | 1, 3 |
| 5 | [Loops and integrations](2026-09-30-plan-5-loops-integrations.md) | Sweep, watcher, merge train, Orca remote transport, Telegram and Slack channels | 1 to 4 |

Plans 2 to 6 were built in three parallel lanes (go: plans 2 and 5; roles: plans 3 and 4; repo: plan 6) against one cross-lane contract, [2026-09-30-v0.1-interfaces.md](2026-09-30-v0.1-interfaces.md). Each lane wrote its plan file first, then implemented it. Each lane had an adversarial review and an independent check, then one whole-branch review for all lanes. Each plan file has its own deviations, verified facts, and decisions that need the owner.

## Deviations from the specification (for owner review)

1. Agent-derived, needs owner decision. Tests use `go test` instead of `bats`. Go is already required for the MCP server (owner decision 2026-09-30: Go, started with `go run`), so no new tool is necessary. Plan 2 tests the shell scripts from Go tests. CI still runs `shellcheck`.
2. Agent-derived, needs owner decision. The MCP server has four tools more than spec section 10.1 lists: `report_read` (bigm reads report files through the server, not by path), `lease_define` (bigm defines a shared resource and its capacity), `lease_list` (a grantor sees requests and grants), and a lock around the lease state, because several sessions write it.
3. Agent-derived, needs owner decision. The MCP server has more tools than spec section 10.1 lists: `question_open`, `session_launch`, `session_resume`, `session_list`, `init_plan`, `init_apply`, `repos_set`, and `bruh_info`. Plugin code writes each file of the plugin data folder (principle 3), so each new kind of file got a tool.
4. The role key grammar is provisional: a task ID has no hyphen, so the last hyphen of a clerk key separates the project from the task (interfaces section 1). Agent-derived, needs owner decision.
5. A start message has the header `START: <subject>`, which spec section 5 does not list. Agent-derived, needs owner decision.
6. Merges: a merge grant names the stable key `clerk-<project>-merge`. Each merge is one task in a new session under that key, so spec 3.6 ("a clerk stops when its task is done") holds. The merger of every project runs on the bigm machine, so bigm may write the settings of, start, and resume a merger clerk; for every other key, only the parent may. Agent-derived, needs owner decision.
7. `mail_post` refuses messages between roles that are not parent and child, except messages from bigm and a P0 from a clerk to bigm. Agent-derived, needs owner decision.
8. Role settings files of every role except bigm turn off the official Telegram plugin, because a second Telegram session takes the bot away from bigm. Agent-derived, needs owner decision.
9. The `deliver` workflow takes two more optional `args` keys: `answers` (the answers of a relaunch with `resumeFromRunId`) and `test_gates` (the gates that must run more than zero tests). Agent-derived, needs owner decision.
